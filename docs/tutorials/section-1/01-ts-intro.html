Overview of the key concepts

A time series is a set of observations indexed by time, where the order matters and neighbouring values are usually related. Before any modelling, the data have to be stored in a form that R recognises as a time series, so that it knows the spacing of the observations and where each one falls in the seasonal cycle.

The ts class. A ts object is a numeric vector with three extra attributes: start, end and frequency. The frequency is the number of observations per cycle (12 for monthly data with a yearly cycle, 4 for quarterly, 52 for weekly). start = c(2021, 1) means period 1 of 2021, so for monthly data January 2021. Periods are numbered from 1, and the second element of start can never exceed the frequency. Once these attributes are set, functions such as window(), lag(), diff(), cycle() and decompose() all know how the data are spaced.

Aggregation. Data are often collected at a finer resolution than we want to model. Daily sales can be summed to monthly totals or averaged to weekly means. The choice of resolution decides which patterns are visible: daily data show a weekly cycle and a yearly cycle, while monthly totals hide the weekly cycle completely.

Lags and differences. The lag operator shifts a series in time, \(BY_t = Y_{t-1}\). Differencing removes structure: the first difference \(\nabla Y_t = Y_t - Y_{t-1}\) removes a linear trend, and the seasonal difference \(\nabla_{12} Y_t = Y_t - Y_{t-12}\) removes a stable 12-month pattern. These are the building blocks of ARIMA and SARIMA models later in the section.

Decomposition. An additive decomposition writes the series as

\[ Y_t = T_t + S_t + R_t, \]

a trend-cycle \(T_t\), a seasonal component \(S_t\) that repeats every \(m\) periods and sums to zero over a cycle, and a remainder \(R_t\). Classical decomposition estimates the trend with a centred moving average, then averages the detrended values for each season. STL does the same job with local regression (loess), lets the seasonal pattern change slowly over time, and is more robust to outliers.

The tidy toolkit. A tsibble is a data frame with an explicit index (the time variable) and key (which series each row belongs to), so many series can live in one table. It also distinguishes implicit gaps (missing rows) from explicit missing values (rows containing NA). feasts provides seasonal plots, ACFs, STL and feature extraction on tsibbles, and timetk produces similar diagnostics directly from an ordinary tibble.

Caution

stats::lag() needs its package prefix: once the tidyverse is loaded, dplyr::lag() masks it, and the two behave differently. dplyr::lag() shifts the values of a vector and pads with NA, while stats::lag() keeps the values and shifts the time attribute of a ts. With k = -1, each value is moved one period later, so lining it up with the original (as in cbind above) gives \(Y_{t-1}\) next to \(Y_t\).

The first difference loses one observation and the seasonal difference loses a full year (12 observations), which matters when the series is short.

Question 7: What is wrong with each call?

Q1. ts(x, start = c(2023, 13), frequency = 12) Monthly data have only 12 periods per year, so the second element of start cannot exceed 12. “Period 13 of 2023” does not exist; it should roll over to January 2024. Fix: ts(x, start = c(2024, 1), frequency = 12).

Q2. ts(x, start = 2023, frequency = 12) For sub-annual data (frequency > 1), start should give both the year and the period within the year. A single number is ambiguous. Fix: ts(x, start = c(2023, 1), frequency = 12).

Q3. ts(x, start = c(2023, 0), frequency = 12) Periods are numbered from 1, so period 0 does not exist; January is period 1. Fix: ts(x, start = c(2023, 1), frequency = 12).

Q4. ts(x, start = c(2023, 2), frequency = 4) “Period 2” depends on the frequency: with frequency = 4 it means Q2, not February. If the data are monthly, the frequency must match their real spacing. Fix: ts(x, start = c(2023, 2), frequency = 12).

Q5. ts(x, start = c(2023, 1), frequency = 12.5) The frequency counts observations per cycle, so it should be a whole number. Most methods built on ts objects (seasonal differencing, decompose(), seasonal ARIMA) need an integer frequency. Fix: ts(x, start = c(2023, 1), frequency = 12).

Q6. ts(x, start = c(2023, 1), frequency = 12, deltat = 1/12) frequency and deltat describe the same thing from two directions (deltat = 1/frequency), so giving both is redundant. Fix: give only one, e.g. ts(x, start = c(2023, 1), frequency = 12).

Q7. ts(x, start = c(2023, 1), frequency = 365) frequency = 365 declares daily data. If x holds monthly values, every value is placed at the wrong point in the yearly cycle. Fix: ts(x, start = c(2023, 1), frequency = 12).

Q8. window(x, start = c(2023, 13)) window() can only extract periods that exist inside the series’ range, and month 13 does not exist. Fix: start at a valid point inside the series, e.g. window(x, start = c(2024, 1)).

Q9. decompose(ts(x, frequency = 1)) With frequency = 1 there is no seasonal cycle, so there is no seasonal component to estimate. decompose() also needs at least two complete cycles. Fix: use the series’ real seasonal frequency, e.g. decompose(ts(x, frequency = 12)).

Implementation in R

To understand what decompose() is doing, I wrote the classical additive decomposition from first principles and checked it against the built-in function on the monthly S001 series.

  1. Trend. With an even period \(m = 12\), a plain 12-term moving average is not centred on a month. A \(2 \times 12\) moving average fixes this: it is a 13-term weighted average with weights \(\tfrac{1}{24}\) on the two end months and \(\tfrac{1}{12}\) on the 11 in between, \[ \hat T_t = \frac{1}{12}\left(\tfrac{1}{2}Y_{t-6} + Y_{t-5} + \dots + Y_{t+5} + \tfrac{1}{2}Y_{t+6}\right). \] The first and last six months have no trend estimate.
  2. Seasonal component. Detrend, \(Y_t - \hat T_t\), average the detrended values for each calendar month, then centre the 12 averages so they sum to zero.
  3. Remainder. \(\hat R_t = Y_t - \hat T_t - \hat S_t\).
Code 
my_decompose <- function(y) {
  m <- frequency(y)
  w <- if (m %% 2 == 0) c(0.5, rep(1, m - 1), 0.5) / m else rep(1, m) / m
  trend <- stats::filter(y, w, sides = 2)

  detrended <- y - trend
  s_means <- tapply(detrended, cycle(y), mean, na.rm = TRUE)
  s_means <- s_means - mean(s_means)            # seasonal effects sum to zero
  seasonal <- ts(s_means[cycle(y)], start = start(y), frequency = m)

  list(trend = trend, seasonal = seasonal, random = y - trend - seasonal,
       figure = s_means)
}

mine  <- my_decompose(sales_ts)
built <- decompose(sales_ts)

max_diff <- c(
  Trend     = max(abs(mine$trend    - built$trend),    na.rm = TRUE),
  Seasonal  = max(abs(mine$seasonal - built$seasonal), na.rm = TRUE),
  Remainder = max(abs(mine$random   - built$random),   na.rm = TRUE)
)
kable(data.frame(Component = names(max_diff), `Max absolute difference` = max_diff,
                 check.names = FALSE), row.names = FALSE, digits = 10)
Component Max absolute difference
Trend 0
Seasonal 0
Remainder 0
Code 
kable(data.frame(Month = month.abb, Effect = as.numeric(mine$figure)), digits = 1)

The differences are zero up to rounding, so decompose() is exactly the moving-average-then-seasonal-means procedure above. Writing it out made the method’s weaknesses concrete. The seasonal pattern is forced to be identical every year, the trend is missing at both ends (exactly where a forecaster needs it most), and one unusual month affects both the moving average and its month’s seasonal mean. STL addresses all three.

Reflection

What was most challenging: Keeping track of the different ways R represents time. A ts object stores time as decimal years with a frequency attribute, a Date column stores calendar dates, and a tsibble uses an index and key. Each has its own rules: start periods are numbered from 1, frequency must match the real spacing of the data, and daily data need the seasonal period stated explicitly because there is more than one cycle. The lag() clash was the most confusing. stats::lag() shifts the time attribute while dplyr::lag() shifts the values, and which one runs depends on which packages are loaded.

What I now understand: Getting the structure of a time series right is part of the analysis, not a preliminary step. The frequency decides what cycle(), seasonal differencing and decomposition do, so a wrong frequency produces output that looks plausible but is meaningless (as in Question 7). Aggregation is a modelling choice too: summing to monthly removes the weekly cycle entirely. The difference between implicit gaps and explicit NAs in a tsibble explained why filling gaps has to happen before aggregating.

Advantages and limitations of the methods:

  • Advantages: Base ts objects are simple and are what most classical functions (arima, decompose, HoltWinters) expect. The tidy tools handle many series at once through the key, deal with irregular dates and gaps explicitly, and make seasonal plots for multiple periods easy.
  • Limitations: A ts object supports only one regular frequency, so it cannot represent daily data with both weekly and yearly cycles. Classical decomposition assumes a fixed seasonal pattern and loses the trend at the ends of the series. Filling missing days with a store mean is convenient for exploration but would bias any model fitted afterwards.

## Overview of the key concepts

A time series is a set of observations indexed by time, where the order matters and neighbouring values are usually related. Before any modelling, the data have to be stored in a form that R recognises as a time series, so that it knows the spacing of the observations and where each one falls in the seasonal cycle.

**The `ts` class.** A `ts` object is a numeric vector with three extra attributes: `start`, `end` and `frequency`. The frequency is the number of observations per cycle (12 for monthly data with a yearly cycle, 4 for quarterly, 52 for weekly). `start = c(2021, 1)` means period 1 of 2021, so for monthly data January 2021. Periods are numbered from 1, and the second element of `start` can never exceed the frequency. Once these attributes are set, functions such as `window()`, `lag()`, `diff()`, `cycle()` and `decompose()` all know how the data are spaced.

**Aggregation.** Data are often collected at a finer resolution than we want to model. Daily sales can be summed to monthly totals or averaged to weekly means. The choice of resolution decides which patterns are visible: daily data show a weekly cycle and a yearly cycle, while monthly totals hide the weekly cycle completely.

**Lags and differences.** The lag operator shifts a series in time, $BY_t = Y_{t-1}$. Differencing removes structure: the first difference $\nabla Y_t = Y_t - Y_{t-1}$ removes a linear trend, and the seasonal difference $\nabla_{12} Y_t = Y_t - Y_{t-12}$ removes a stable 12-month pattern. These are the building blocks of ARIMA and SARIMA models later in the section.

**Decomposition.** An additive decomposition writes the series as

$$
Y_t = T_t + S_t + R_t,
$$

a trend-cycle $T_t$, a seasonal component $S_t$ that repeats every $m$ periods and sums to zero over a cycle, and a remainder $R_t$. Classical decomposition estimates the trend with a centred moving average, then averages the detrended values for each season. **The tidy toolkit.** A `tsibble` is a data frame with an explicit **index** (the time variable) and **key** (which series each row belongs to), so many series can live in one table. ### Question 7: What is wrong with each call?

**Q1. `ts(x, start = c(2023, 13), frequency = 12)`**
Monthly data have only 12 periods per year, so the second element of `start` cannot exceed 12. "Period 13 of 2023" does not exist; it should roll over to January 2024.
Fix: `ts(x, start = c(2024, 1), frequency = 12)`.

**Q2. `ts(x, start = 2023, frequency = 12)`**
For sub-annual data (`frequency > 1`), `start` should give both the year and the period within the year. A single number is ambiguous.
Fix: `ts(x, start = c(2023, 1), frequency = 12)`.

**Q3. `ts(x, start = c(2023, 0), frequency = 12)`**
Periods are numbered from 1, so period 0 does not exist; January is period 1.
Fix: `ts(x, start = c(2023, 1), frequency = 12)`.

**Q4. `ts(x, start = c(2023, 2), frequency = 4)`**
"Period 2" depends on the frequency: with `frequency = 4` it means Q2, not February. If the data are monthly, the frequency must match their real spacing.
Fix: `ts(x, start = c(2023, 2), frequency = 12)`.

**Q5. `ts(x, start = c(2023, 1), frequency = 12.5)`**
The frequency counts observations per cycle, so it should be a whole number. Most methods built on `ts` objects (seasonal differencing, `decompose()`, seasonal ARIMA) need an integer frequency.
Fix: `ts(x, start = c(2023, 1), frequency = 12)`.

**Q6. `ts(x, start = c(2023, 1), frequency = 12, deltat = 1/12)`**
`frequency` and `deltat` describe the same thing from two directions (`deltat = 1/frequency`), so giving both is redundant.
Fix: give only one, e.g. `ts(x, start = c(2023, 1), frequency = 12)`.

**Q7. `ts(x, start = c(2023, 1), frequency = 365)`**
`frequency = 365` declares daily data. If `x` holds monthly values, every value is placed at the wrong point in the yearly cycle.
Fix: `ts(x, start = c(2023, 1), frequency = 12)`.

**Q8. `window(x, start = c(2023, 13))`**
`window()` can only extract periods that exist inside the series' range, and month 13 does not exist.
Fix: start at a valid point inside the series, e.g. `window(x, start = c(2024, 1))`.

**Q9. `decompose(ts(x, frequency = 1))`**
With `frequency = 1` there is no seasonal cycle, so there is no seasonal component to estimate. `decompose()` also needs at least two complete cycles.
Fix: use the series' real seasonal frequency, e.g. `decompose(ts(x, frequency = 12))`.

## Implementation in R

To understand what `decompose()` is doing, I wrote the classical additive decomposition from first principles and checked it against the built-in function on the monthly S001 series.

1. **Trend.** With an even period $m = 12$, a plain 12-term moving average is not centred on a month. A $2 \times 12$ moving average fixes this: it is a 13-term weighted average with weights $\tfrac{1}{24}$ on the two end months and $\tfrac{1}{12}$ on the 11 in between,
$$
\hat T_t = \frac{1}{12}\left(\tfrac{1}{2}Y_{t-6} + Y_{t-5} + \dots + Y_{t+5} + \tfrac{1}{2}Y_{t+6}\right).
$$
The first and last six months have no trend estimate.
2. **Seasonal component.** Detrend, $Y_t - \hat T_t$, average the detrended values for each calendar month, then centre the 12 averages so they sum to zero.
3. **Remainder.** $\hat R_t = Y_t - \hat T_t - \hat S_t$.

```{r}
#| label: own-decompose
my_decompose <- function(y) {
  m <- frequency(y)
  w <- if (m %% 2 == 0) c(0.5, rep(1, m - 1), 0.5) / m else rep(1, m) / m
  trend <- stats::filter(y, w, sides = 2)

  detrended <- y - trend
  s_means <- tapply(detrended, cycle(y), mean, na.rm = TRUE)
  s_means <- s_means - mean(s_means)            # seasonal effects sum to zero
  seasonal <- ts(s_means[cycle(y)], start = start(y), frequency = m)

  list(trend = trend, seasonal = seasonal, random = y - trend - seasonal,
       figure = s_means)
}

mine  <- my_decompose(sales_ts)
built <- decompose(sales_ts)

max_diff <- c(
  Trend     = max(abs(mine$trend    - built$trend),    na.rm = TRUE),
  Seasonal  = max(abs(mine$seasonal - built$seasonal), na.rm = TRUE),
  Remainder = max(abs(mine$random   - built$random),   na.rm = TRUE)
)
kable(data.frame(Component = names(max_diff), `Max absolute difference` = max_diff,
                 check.names = FALSE), row.names = FALSE, digits = 10)
```

```{r}
#| label: tbl-seasonal-figure
#| tbl-cap: "Estimated seasonal effects by month (own implementation)."
kable(data.frame(Month = month.abb, Effect = as.numeric(mine$figure)), digits = 1)
```

The differences are zero up to rounding, so `decompose()` is exactly the moving-average-then-seasonal-means procedure above. Writing it out made the method's weaknesses concrete. The seasonal pattern is forced to be identical every year, the trend is missing at both ends (exactly where a forecaster needs it most), and one unusual month affects both the moving average and its month's seasonal mean. STL addresses all three.

## Reflection

**What was most challenging:** Keeping track of the different ways R represents time. A `ts` object stores time as decimal years with a frequency attribute, a `Date` column stores calendar dates, and a `tsibble` uses an index and key. Each has its own rules: `start` periods are numbered from 1, frequency must match the real spacing of the data, and daily data need the seasonal period stated explicitly because there is more than one cycle. The `lag()` clash was the most confusing. `stats::lag()` shifts the time attribute while `dplyr::lag()` shifts the values, and which one runs depends on which packages are loaded.

**What I now understand:** Getting the structure of a time series right is part of the analysis, not a preliminary step. The frequency decides what `cycle()`, seasonal differencing and decomposition do, so a wrong frequency produces output that looks plausible but is meaningless (as in Question 7). Aggregation is a modelling choice too: summing to monthly removes the weekly cycle entirely. The difference between implicit gaps and explicit `NA`s in a tsibble explained why filling gaps has to happen before aggregating.

**Advantages and limitations of the methods:**

- *Advantages:* Base `ts` objects are simple and are what most classical functions (`arima`, `decompose`, `HoltWinters`) expect. The tidy tools handle many series at once through the key, deal with irregular dates and gaps explicitly, and make seasonal plots for multiple periods easy.
- *Limitations:* A `ts` object supports only one regular frequency, so it cannot represent daily data with both weekly and yearly cycles. Classical decomposition assumes a fixed seasonal pattern and loses the trend at the ends of the series. Filling missing days with a store mean is convenient for exploration but would bias any model fitted afterwards.
